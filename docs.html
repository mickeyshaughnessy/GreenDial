GreenDial API

REST API for the GreenDial health assistant. All endpoints return JSON. Base URL: https://greendial.org

Overview

GreenDial is a personal health platform powered by Doc, an AI coordinator, and a team of nine specialist health agents. Doc guides conversations, builds the user's health profile, and routes specialist questions to the right agent. Agents also run on a server-side cron schedule, sending proactive check-ins as notifications.

Authentication is username + passphrase. Third-party integrations use HTTP Basic Auth.

How agents activate

1. Via Doc (chat-triggered) — When a user's message matches an agent's keyword list, or when Doc emits a **CALL_AGENT** directive, the server runs the specialist agent and feeds its response back to Doc as context. Doc synthesizes a reply that weaves in expert knowledge naturally.

2. Via crontab (scheduled) — agent_runner.py runs on the production VM at scheduled intervals. For each user with active agent subscriptions, it generates a personalized check-in notification from each subscribed agent. Users see these in the notification bell.

All agents are kind, helpful, and truthful. They always recommend professional consultation for medical decisions and never diagnose.

Agents

Manage which specialist agents a user subscribes to. Subscribed agents generate daily personalized notifications via cron. Agents also activate automatically during chat based on keyword matching and Doc's dispatch decisions.

GET /agents/{user_id}
Get the user's current subscriptions and the full list of available agents.
GET /agents/user_alice { "subscriptions": ["diet", "sleep"], "agent_prefs": {"diet": {"style": "plant-based"}}, "available_agents": [ {"id": "diet", "name": "Diet Advisor", "emoji": "🥗", "subscribed": true}, {"id": "exercise","name": "Exercise Coach", "emoji": "💪", "subscribed": false}, ... ] }
PUT /agents/{user_id}
Update agent subscriptions, per-agent preferences, and custom agent prompt.
FieldTypeDescription
subscriptionsstring[]Agent IDs to subscribe to. Unrecognized IDs are silently dropped.
agent_prefsobjectPer-agent preferences (merged with existing)
custom_agent_promptstringSystem prompt for the Custom agent (max 2000 chars)
PUT /agents/user_alice {"subscriptions": ["diet", "sleep", "mental_health"], "agent_prefs": {"sleep": {"goal_hours": 8}}, "custom_agent_prompt": "You are a longevity coach focused on Blue Zone habits."}
Cron runner: agent_runner.py runs on the production VM. Each subscribed agent is run once per 20 hours per user. Results are appended to the user's notification list (max 20 notifications kept). Run manually with:
python3 agent_runner.py --agent diet --user user_alice --dry-run

How Doc Works

Doc is the primary coordinator. Its behavior is controlled by a dynamically assembled prompt. At each turn, the server may run up to one specialist agent and inject its response as context before Doc's final reply.

Doc runs on an LLM via OpenRouter. Two structured markers are stripped server-side before returning text to the user:
• **PROFILE_UPDATE** {"field": "value"} — saves health data to the user's profile
• **CALL_AGENT** {"agent": "sleep"} — triggers a specialist agent sub-call

Agent dispatch flow

1. User sends message 2. Server checks keyword → agent matches 3. Doc generates response (may include **CALL_AGENT**) 4. If agent identified: a. Specialist agent runs with user profile + transcript b. Agent returns 2-4 sentence expert response c. Doc re-runs with agent response as AGENT CONTEXT d. Doc synthesizes a natural, expert-informed reply 5. Server strips **CALL_AGENT** and **PROFILE_UPDATE** markers 6. Final response returned to browser
Core Identity
You are Doc, a proactive health assistant. You lead the conversation to build the user's health profile and provide guidance.
Profile Update Instructions (injected when profile is incomplete)
## PROFILE UPDATES When the user shares health info, emit: **PROFILE_UPDATE** {"field": "value"} Operations: - Set: {"age": "44"} — sets the field - Append: {"medications": "+aspirin"} — adds to existing (use + prefix) - Delete: {"allergies": null} — removes the field - Nested: {"vitals": {"bp": "120/80"}} — creates sub-object Fields: primary_concern, health_conditions, medications, allergies, age, weight, height, location, diet_type, exercise_frequency, exercise_type, sleep_hours, sleep_quality, stress_level, goals, notes Example — User says "I'm 44 and have diabetes": **PROFILE_UPDATE** {"age": "44", "health_conditions": "diabetes"}
Style Mirroring (injected based on user's detected tone & message length)
## YOUR STYLE User writes briefly. Match them: 1-2 short sentences max. No fluff. — or — ## YOUR STYLE User writes moderate length. Match them: 2-3 sentences. Be conversational. — or — ## YOUR STYLE User writes detailed messages. You can be more thorough, but stay focused. ## TONE User is casual/informal. Match their energy. Use contractions, be relaxed. — or — ## TONE User is formal. Be professional and clear.
Profile Status (one of three variants)
## PROFILE STATUS Empty - gather basic info: why they're here, any health conditions, goals. — or — ## PROFILE STATUS Partial - missing: primary_concern, goals ## CURRENT PROFILE {"health_conditions": "type 2 diabetes", "age": "44", ...} — or — ## PROFILE STATUS Complete. Focus on their goals and providing helpful responses. ## CURRENT PROFILE {...full profile...}
Conversation History (injected when available)
## CONVERSATION SUMMARY {summary of older exchanges} ## RECENT CONVERSATION User: I've been feeling tired lately Doc: How long has that been going on? Have you had any changes in sleep? User: About two weeks, sleep is fine Doc: ...
Response Rules (always injected)
## RULES - ALWAYS end your response with exactly ONE question to drive the conversation forward - NEVER wait for the user to initiate a topic. You lead. - Match the user's message length - Only update profile with info they explicitly stated
Final instruction (always appended)
--- User: {user_input} Doc (respond appropriately, then ask ONE leading question):
